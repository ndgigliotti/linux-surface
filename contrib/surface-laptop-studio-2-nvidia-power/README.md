# Surface Laptop Studio 2 NVIDIA runtime-power workaround

This optional example addresses a sustained 10 W NVIDIA restriction after
runtime resume on one Surface Laptop Studio 2 / RTX 4060 configuration while
retaining finegrained RTD3. It is an interim workaround for review, not a
complete Surface platform power-controller driver or a general laptop fix.

See the [diagnosis and physical test report](https://github.com/linux-surface/linux-surface/issues/2185#issuecomment-5962487523)
and [NVIDIA power-source report](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/483#issuecomment-5962485298).

## What is included

- `nvidia-power-source-fallback.patch`: query Linux's power_supply class when
  NVIDIA has no ACPI `_PSR` device. This partial change corrects source reporting
  but did **not** independently remove the observed 10 W restriction.
- `surface-nvidia-power.py`: based on the physically tested helper, with the
  review fixes described below. It polls
  read-only PCI runtime-state and AC-source sysfs files every 200 ms. After
  observing an active D0 GPU, it creates a temporary NVIDIA RM client, reports
  actual AC/battery state, selects auxiliary P0 and verifies source readback.
  Every update releases the client and device descriptors.
- `surface-nvidia-power.nix`: based on the tested NixOS service module, with
  startup retries added after review and an assertion for NVIDIA 595.71.05.
  It does not itself apply the driver patch.
- `surface-nvidia-power.service`: conventional systemd-unit example, adapted
  from that module; this unit has not been activated on another distribution.
- `test_surface_nvidia_power.py`: mocked policy tests and hardware-free
  service-startup checks.
- Targeted counterfactual/compute logs and `gen16-postboot-validation.json`:
  physical evidence, not results generated by the mocked tests.

The post-review helper caches the AC/battery source actually applied after RM
allocation, so a rapid charger transition cannot leave an obsolete source
cached indefinitely. An unknown source at that re-read fails before policy
controls are issued. Both service examples check for the NVIDIA character
device nodes before starting the helper and retry every three seconds if they
are absent. These checks only stat the nodes. Start-rate limiting is disabled
so delayed node creation cannot exhaust the retries; other service failures
also continue to retry until the service is stopped.

These review fixes have hardware-free regression coverage and configuration
checks, but have not been activated or physically tested. The supplied physical
logs describe the earlier installed helper/module.

The helper does not set a wattage limit, modify ACPI tables, call SGPC `_DSM`,
hold an idle RM client or disable NVIDIA runtime power management. It uses the
published RM controls SET_POWERSTATE (`0x2080205b`) and SET_AUX_POWER_STATE
(`0x20802092`). Auxiliary P0 differs from the GPU's performance P-state.

## Exact tested configuration and guards

The physical tests used NixOS 26.05, Surface Linux 6.19.8, NVIDIA **595.71.05
open kernel module** with matching userspace/GSP, Intel-primary PRIME offload,
`NVreg_DynamicPowerManagement=0x02`, no persistence daemon, original Surface
Connect charger and no external display/dock.

The helper deliberately rejects a machine unless all of these match:

- DMI product: `Surface Laptop Studio 2`.
- GPU at `0000:01:00.0`: vendor/device `10de:28a0`, subsystem `1414:0083`.
- Loaded NVIDIA version: `595.71.05`.
- SGPC platform device `MSHW0216:00` exists without a bound driver.
- A GPU SSDT has SHA-256
  `86e842eae5254dbb6e5d04bd298db01d9b4505d4cc357d6b781afb40258dea99`.
- AC source is exposed at `/sys/class/power_supply/ADP1/online`.

A different firmware, GPU model, driver or adapter layout requires review and
new physical validation. Do not delete guards simply to make the helper run.
The same-version proprietary kernel module has not been compared.

## Diagnosis and results

The GPU firmware power resource `PRPD._ON` sends D5 when `SGPC.SACT != 1`.
A temporary kprobe observed this during a real GPU wake. NVIDIA maps D5 to
auxiliary P4. The controlled P4 -> P0 -> P4 test changed the enforced cap
10 -> 60 -> 10 W (`gen15-aux-counterfactual.log`). No Linux SGPC driver was bound.

With the query fallback alone, the restriction persisted. With the installed
helper as well, ~30-second clpeak computation produced 13 steady samples at
100% utilization: 60 W enforced, 59.91–60.09 W draw, 2205–2430 MHz, peak 66 C.
Float throughput was **14.25384 TFLOPS** versus **1.24670 TFLOPS** under the cap;
a second wake produced **13.63473 TFLOPS**. Both returned to
D3cold/suspended with runtime usage zero, and the idle helper had no GPU FDs.
Battery computation and live AC -> battery -> AC transitions passed earlier
with helper code differing only by a trailing blank line.

The C query fallback applies to NVIDIA main 615.71.09, but that release has
not been built or physically tested here. The helper still refuses that driver.

## Remaining limitations

Native NVIDIA GPU thermal/power limits remain operative. Clearing auxiliary
P4 does **not** implement the missing Surface platform power-budget policy or
establish that unconditional P0 is appropriate for other chargers or systems.
Alternative/undersized chargers, docks/external displays, system suspend/wake,
repeated inference and measured electrical/battery savings remain unvalidated.

There can be up to a polling interval of userspace correction delay. The active
sysfs check and subsequent device open are not atomic: suspend can race the
open. The helper is not a guarantee that a GPU can never wake in that window.
Repeated measured returns to idle D3cold are the established result.

Stopping the helper restores auxiliary P4 if the GPU is observed active; it
does not intentionally open an observed idle GPU just to restore the next
wake's firmware restriction. A hard process kill bypasses that restoration.
After removal, firmware D5 on a later wake can restore the original cap.

## Installation example

Review this example for your system first and retain a known-working recovery
configuration. The helper requires root for its guarded RM controls and firmware
table reads. Python uses only its standard library on the tested 64-bit ABI.

1. Keep Intel as the desktop renderer and enable NVIDIA PRIME offload and
   finegrained RTD3. Keep persistence disabled. Do not use an always-on GPU as
   the workaround's acceptance condition.
2. Apply `nvidia-power-source-fallback.patch` through your distribution's
   **595.71.05 open-module** packaging. Build against your kernel and retain
   matching userspace/GSP. Module signing/trust requirements depend on your
   kernel; successful Secure Boot of the OS is not proof of module-signature
   enforcement. Do not install mismatched modules or unload a GPU used by the
   desktop.
3. On NixOS, copy the Python helper/module alongside your configuration, import
   the module and add the fallback patch to `hardware.nvidia.package.open`
   using `overrideAttrs`. Pin the matching driver version. The module's
   version assertion is intentional. Review/build the candidate before any
   attended activation; preserve tested boot/recovery paths.
4. On a conventional systemd distribution, adapt the unit's Python and `test`
   executable paths, then
   install the helper at `/usr/local/libexec/surface-nvidia-power.py` and the
   unit at `/etc/systemd/system/surface-nvidia-power.service`. Enable it only
   after the guards and matching patched module are validated. This packaging
   route is an example, not a tested cross-distribution installation.

## Validation and removal

Run the hardware-free tests without root or GPU access:

```sh
python3 -m unittest discover -s . -p 'test_surface_nvidia_power.py' -v
```

The startup checks use the installed `test` executable against temporary paths
and symlinks to `/dev/null`; they do not open NVIDIA devices or start services.
The NixOS module check uses `nix-instantiate` with stub packages, without fetching,
building or activation, and is skipped if Nix is unavailable.

For physical validation, record charger, display/dock, firmware, kernel and
driver. Verify Intel default rendering and NVIDIA offload, then run a bounded
compute workload and observe sustained performance/power/temperature. After
the workload exits, read PCI sysfs to confirm D3cold/suspended and usage zero.
Do not poll `nvidia-smi` while assessing idle: it can wake the GPU. Inspect
service logs, restarts, idle `/proc/<service-pid>/fd`, and kernel Xid/assertions.
Validate truthful AC/battery transitions with an attended charger test.

Remove the service import/enablement and fallback patch through the same
packaging mechanism used to add them. Build/boot the replacement with recovery
preserved before retiring its predecessors. Never remove recovery generations
or GC store outputs merely to undo this example.

## Platform follow-up

A permanent implementation needs maintainers to determine the SGPC/SMF
protocol, supported firmware and legitimate AC/battery/charger/platform-budget
transitions, including suspend/resume and teardown. The supplied helper is
evidence and an opt-in interim implementation; it does not replace that design.
